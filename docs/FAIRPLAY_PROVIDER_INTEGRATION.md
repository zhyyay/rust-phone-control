# Authorized FairPlay SAP Provider Integration

## Current receiver boundary

The receiver implements AirPlay discovery, RTSP request framing, controller pairing/approval, FairPlay FPLY message parsing and state validation, stream setup validation, mirror packet handling, and the Windows Media Foundation H.264 decoder path.

It does **not** implement Apple's proprietary FairPlay SAP cryptographic transform. The default RTSP server intentionally has no provider and returns `501 Not Implemented` to an M1 request. This is fail-closed behavior, not a transient pairing error.

## Supported integration point

Implement `airplay::FairPlaySapProvider` in a separately licensed/authorized adapter and start the receiver through:

```rust
crate::airplay::start_with_fairplay_provider(Arc::new(AuthorizedProvider::new()?))
```

The ordinary `airplay::start()` path remains provider-free and fail-closed.

The provider contract is connection-scoped:

1. `begin(&FairPlayMessage)` receives a parsed M1 record and must return a genuine, authenticated M2 challenge generated by the authorized SAP implementation.
2. `finish(initial, challenge, key_message)` must authenticate M3 against that exact M1/M2 exchange. It may return media keys only after successful authentication.
3. Return `UnsupportedMode`, `InvalidMessage`, `AuthenticationFailed`, or `Unavailable` accurately. Do not downgrade an authentication failure into success.

The RTSP layer owns the provider session boundary and zeroizes parsed message buffers, challenges, acknowledgements, and returned key wrappers when their connection-scoped values are dropped.

## Security requirements

- Do not generate placeholder or random M2 challenges.
- Do not replay captured M2/M4 messages or use fixed/test media keys.
- Do not derive or guess media keys from M1/M3 fields.
- Do not log raw FairPlay messages, challenge bytes, wrapped keys, IVs, or derived keys.
- Do not bundle unlicensed Apple code, reverse-engineered SAP tables, or incompatible copyleft implementations.
- Keep the provider implementation and its licensing/provenance separate from this Apache-2.0 receiver.

## Acceptance tests for an authorized provider

Before enabling it in a release build, verify:

- A real iPhone M1 produces a valid provider-generated M2 response.
- A matching M3 is authenticated and yields connection-scoped media keys.
- Altered M3, replayed M3, mismatched M1/M2, unsupported modes, and provider failures are rejected.
- No media stream SETUP succeeds before M3 authentication.
- A valid SETUP's ekey/eiv are combined only with the authenticated session keys in the existing mirror pipeline.
- TEARDOWN, RTSP disconnect, failed authentication, and renegotiation clear the session's key material.
- Tests use authorized test vectors supplied with the licensed provider; no captured production phone keys are committed.

## Work that can proceed without the provider

The discovery, pairing, RTSP state machine, stream descriptor validation, bounded media sockets, packet parsing, H.264 decoder, and preview mailbox can be tested independently. A successful control connection or a bound media port must never be presented as a successful decoded mirror until a real decoded frame reaches the preview mailbox.
